# R-003：运行时缺陷修复（连接池、生产密钥、BFF 错误映射）

- 状态：confirmed（2026-11-27，用户确认 worker 口径、BFF 超时与验收阈值）
- 优先级：P0（BUG-002 为生产安全阻断）；P1（BUG-001 / BUG-003）
- 提出人 / 日期：用户 / 2026-11-27
- 决策人：用户
- 关联任务：待建
- 关联 ADR：待建（生产密钥策略、连接池容量、网关错误契约）

## 1. 背景与问题

| 编号 | 优先级 | 现象 | 根因 |
| --- | --- | --- | --- |
| BUG-001 | P1 | 100 并发持续请求时大量超时，成功率约 27.54%，日志出现 `QueuePool limit size 5 overflow 10 reached` | `create_engine` 使用 SQLAlchemy 默认池容量（size=5 / overflow=10），同步接口线程数远大于连接数，等待 30 秒后失败 |
| BUG-002 | P0 | 生产 Compose 未设置敏感变量时仍使用开发默认 JWT 密钥与 root 密码；出现 JWT 密钥过短警告 | Compose 使用 `${VAR:-默认值}` 静默回退；应用配置无生产态强校验 |
| BUG-003 | P1 | 后端上游不可用时 `/api/backend/api/health` 返回 500 | BFF 的 `fetch` 未捕获连接拒绝/超时，异常直落 Next.js 默认 500 |

## 2. 目标（可观测）

1. 100 并发压测下核心 API 成功率 ≥99%、P95 ≤1.5s、日志 0 条 `QueuePool limit`；池耗尽时返回 503 而非超时/500。
2. 生产环境缺少或使用弱密钥时启动即失败，日志给出明确原因；数据库使用最小权限应用账号。
3. BFF 上游连接失败返回 502、超时返回 504，响应为统一结构且不泄露内部地址与堆栈。

## 3. 范围（做）

### BUG-001 连接池

1. 后端改为多 worker：`workers = min(4, CPU//2, 内存GB)`，至少 1，`WEB_CONCURRENCY` 可覆盖；每 worker 连接池 `pool_size=10`、`max_overflow=10`。
2. `Settings` 新增 `db_pool_size=10`、`db_pool_max_overflow=10`、`db_pool_timeout=5.0`、`db_pool_recycle=1800`；`create_engine` 显式传入，抽出 `build_engine` 便于单测。
3. `errors.py` 注册 `sqlalchemy.exc.TimeoutError` → 503「服务繁忙，请稍后重试」，记录 trace id。
4. 生产 Compose 注入容量参数，并按 `workers × (pool_size + overflow) ≤ MySQL max_connections - 余量` 核算。

### BUG-002 生产密钥

1. Compose 敏感变量改为必填：`${MYSQL_ROOT_PASSWORD:?...}`、`${BACKEND_JWT_SECRET:?...}`，healthcheck 同步。
2. `Settings` 增加生产态校验（`debug=False` 时）：JWT 密钥非默认且 ≥32 字节；数据库密码非空/非 `root` 且 ≥12 字符；不满足则启动失败。
3. 本期不强制切换非 root 数据库账号，保留为后续加固项。
4. 新增 `deploy/.env.prod.example`（仅占位符）与密钥生成说明。

### BUG-003 BFF

1. 上游 `fetch` 增加 `BACKEND_FETCH_TIMEOUT_MS`（普通接口默认 60000、导出接口 300000）与 `AbortSignal.timeout`；通过多 worker/多线程避免正常请求触达超时。
2. 连接拒绝/DNS 等网络错误 → 502；超时 → 504；后端正常 4xx/5xx 继续透传。
3. 统一返回 `{code, data:null, message}`，带 `x-trace-id`、`retry-after: 5`，消息脱敏。
4. 服务端按 trace id 记录错误类型，不记录上游地址与堆栈。

## 4. 非范围（不做）

- 不把后端改造成全异步 SQLAlchemy。
- 不引入 Docker secrets / 云密钥管理（列为后续增强）。
- 不改变后端正常 4xx/5xx 的业务语义，不做全局重试。
- 不做前端错误页改版；仅保证错误码可区分。

## 5. 验收标准

| # | 场景 | 操作 | 期望 | 证据 |
| --- | --- | --- | --- | --- |
| 1 | 100 并发 | 对核心读接口压测持续 60s | 成功率 ≥99%，P95 ≤1.5s，0 条连接池超限 | 压测脚本输出 |
| 2 | 池耗尽快速失败 | 临时将 `pool_timeout` 调至 1ms 并压测 | 返回 503 统一结构，不返回 500/不挂起 | pytest / 手工 |
| 3 | 缺密钥启动 | 清空 `BACKEND_JWT_SECRET` 执行 compose config/up | 非零退出并提示必须设置 | 命令输出 |
| 4 | 弱密钥启动 | 设置默认或 <32 字符密钥启动 backend | 启动失败，日志说明原因 | 容器日志 |
| 5 | 合法生产配置 | 强随机密钥 + 应用账号 | healthcheck 通过，登录与核心接口可用 | 手工验证 |
| 6 | 上游拒绝 | `BACKEND_ORIGIN` 指向未监听端口请求 `/api/backend/api/health` | 502，消息不含内部地址 | vitest / curl |
| 7 | 上游超时 | 上游挂起，超时设为 1s | 504，耗时接近 1s | vitest 假时钟 |
| 8 | 现有 BFF 行为 | 登录、401 清 Cookie、CSV 透传 | 无回归 | 现有 vitest |

## 6. 约束

- 安全：生产启动失败优先于带默认密钥运行；错误响应不得包含上游地址、SQL、堆栈、密钥。
- 容量：连接池总连接数必须为 MySQL `max_connections` 留出运维与迁移余量。
- 兼容：本地开发仍允许默认值（`debug=True`）；生产必须显式配置。
- 测试执行：按改动范围跑冒烟，后端全量与 CI 在合并前跑绿。

## 7. 依赖与风险

- 依赖：现有 Compose、MySQL 初始化方式、BFF 路由与测试、后端全局异常处理。
- 风险：
  - 调大连接池可能超过 MySQL 连接上限或容器内存，需要按实例数核算。
  - 已有本地 `.env` 含弱值时升级后会启动失败，属预期，但需更新部署说明。
  - 改为非 root 应用账号涉及已有数据卷的账号初始化，需要在部署步骤中处理。
  - 超时阈值过短可能误伤慢查询导出接口，需要按接口区分或取 10s。
- 回退：连接池参数与超时均为环境变量，可即时回退；密钥校验可通过修复配置回退，不建议关闭校验。

## 8. 优先级与决策

- BUG-002 为 P0，必须最先修；BUG-001 与 BUG-003 为 P1。
- 建议一个批次三个小提交，合并前补一份 ADR 与三份审查记录。
- 发布阻塞关系：三项均应在下次生产部署前完成；BUG-002 未修不得上线。

## 9. 已确认决策（2026-11-27）

1. 后端使用多 worker，按 CPU 与内存分配：`workers = min(4, CPU//2, 内存GB)`，至少 1，`WEB_CONCURRENCY` 可覆盖；每 worker 连接池 10+10。
2. 非 root 数据库账号不是本期必须项；但必须阻断伪造 JWT：生产启动校验强密钥，Compose 缺变量即失败。
3. BFF 保留超时但放宽：普通接口 60s、导出接口 300s，并通过多 worker/多线程扩容避免正常请求超时；只有真实挂起返回 504。
4. 压测口径确认：100 并发、持续 60s、成功率 ≥99%、P95 ≤1.5s、0 条连接池超限。
5. 先补 ADR-012 再实施。

## 10. 可行性初判（助手填写）

三项均为局部改动，不改变服务边界：连接池与异常处理在后端基础设施层；密钥校验在配置与部署层；BFF 错误映射在现有路由内。无新增外部依赖，可通过环境变量回退。最大未知是生产实例数与数据库账号切换方式，需用户确认后固化验收阈值。
