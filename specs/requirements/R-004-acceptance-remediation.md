# R-004 验收反馈整改方案

- 编号：R-004
- 优先级：P0（阻塞上线）
- 来源：`z_测试反馈/acceptance-review/`，被测 HEAD `ca24eb2`
- 结论：反馈判定“不通过，不建议部署”；本方案先区分真实缺陷与验收口径问题，再分批修复与复测。

## 1. 反馈事实

160 条用例：通过 70、失败 88、不适用 2。失败集中在接口测试（75 条）、并发（8 条）、部署（3 条）、功能流程（2 条）。

关键点：**75 条接口失败里，绝大多数实际结果是“请求成功，但数据库/联动副作用未闭环取证”**，并非接口报错。真正有明确故障证据的只有教师认证、投票、BFF 三类；其中后两类需要先复验测试口径。

## 2. 分类

### A. 当前工作区已修，反馈基于旧 HEAD

| 问题 | 现状 | 复验方式 |
| --- | --- | --- |
| BFF 上游不可用返回 500 | 已映射 502/504，带 trace 与脱敏消息 | 断连/超时故障注入 |
| 生产默认 JWT/root 口令 | Compose 必填变量 + `debug=False` 强校验 | 缺变量 `compose config` 失败 |
| 100 并发连接池耗尽 | 多 worker + 可配置连接池 + 503 快速失败 + 缓存 | 100 VU 压测 |
| 无反向代理边界 | 已加 Nginx 限流配置，但后端端口仍直接映射 | 需收口端口 |

验收时必须以当前分支重新执行，不能复用旧 HEAD 结论。

### B. 待复验的疑似误判

1. **教师认证未落库**：`certify_answer` 调用 `set_certified_flag` 后 `db.commit()`，代码路径具备持久化；反馈中的数据库查询可能处于旧事务快照（REPEATABLE READ）。需用新连接、提交后立即查询复验。
2. **投票未落库/重复投票**：spec E-04 明确“保持唯一有效投票，允许修改或取消”，即同值再次提交是**取消**。反馈把重复同值提交期望为 200/409 幂等，与 spec 不一致；其数据库检查在“取消”之后执行，看到 0 行是正确结果。需按 toggle 语义重写断言：首次 +1 落库、重复同值删除、异值改票。
3. 部分 404/400 用例使用了占位 ID（如 999999、invalid），只能证明错误码，不能证明目标对象的业务副作用。

### C. 真实待修

1. **申诉页面与后端规则不一致**：后端允许“存在 executed 处置工单”的用户申诉，页面仅允许 `status === "banned"`，导致非封禁但内容被处置的用户无法提交。
2. **部署边界**：`backend` 仍以 `${BACKEND_PORT}:8000` 暴露到宿主机；应只允许 Nginx 对外，后端端口绑定 127.0.0.1 或移除。
3. **升级/回滚未闭环**：无版本化镜像 tag、回滚脚本；备份恢复未做“恢复后应用读写”演练。
4. **并发验收未按正式口径**：反馈为快速档（每阶段 10s），且基于旧连接池；正式门槛是 100 VU 混合旅程、稳态 ≥30 分钟、P95 ≤800ms、P99 ≤2s、错误率 <1%。
5. **API 副作用证据链缺失**：60+ 条写接口没有逐条数据库断言，被统一判失败。

## 3. 修改方案

### Phase 0 复验（先做，避免修错）

- 用独立脚本对当前分支复验：认证落库、投票 toggle、BFF 502/504、生产密钥门禁、100 VU。
- 每个数据库断言使用**新连接**，并在 HTTP 成功后 `commit/rollback` 旧事务再查询。
- 产出 `docs/审查记录/验收整改/Phase0-复验.md`，明确“真实缺陷 / 测试误判”。

验收：认证响应 true 且新连接查到 1；投票首次落库、重复同值删除、异值改票；四项证据齐全。

### Phase 1 代码修复

- 申诉入口：按确认后的规则统一页面与后端（见未决项 2）。
- 若 Phase 0 证实认证/投票确有缺陷，再修事务与幂等；否则只修测试断言。
- 部署边界：后端端口改 `127.0.0.1:${BACKEND_PORT}:8000` 或移除；Nginx 为唯一公网入口；`/internal` 不对外。

验收：pytest/vitest 相关用例通过；`docker compose config` 通过；端口扫描只看到 Nginx。

### Phase 2 验收工具修正

- 把“写接口统一判失败”改为逐用例断言：HTTP 状态、响应 schema、数据库状态、审计/通知、越权。
- 修正投票断言为 toggle；认证断言用新连接；占位 ID 用例只校验错误语义。
- 重新生成 160 条工作簿与证据，旧结论保留但标注“口径修正”。

验收：新工作簿无“证据不足”类失败；每条失败都有可复现的代码/契约原因。

### Phase 3 部署错误说明（本机不执行部署）

用户已确认本机不做部署。本阶段只做两件事：

- 把反馈中的部署错误、触发条件和影响写清楚，纳入审查记录；
- 输出目标服务器上的操作清单与验收项，实际升级/回滚/恢复演练在目标环境执行，不在本机执行。

已知部署错误：

1. **网络边界**：生产 Compose 直接发布 `${BACKEND_PORT}:8000`，没有反向代理；隔离后端 `/internal/agent/*` 无服务令牌返回 401，说明路径可达，只是靠令牌保护。MySQL 未发布端口，符合预期。
2. **升级/回滚**：只有 Alembic `upgrade head` 实测；没有上一版本镜像 tag、版本化回滚脚本，未执行 downgrade，DEPLOY-005 判阻塞。
3. **恢复库**：恢复快照比应用 schema 旧，首次登录 500（缺 `users.banned_until`），升级到 head 后注册/登录/改资料/读资料通过；进程重启后数据仍在。未做容器级重启与完整备份恢复演练。
4. **密钥**：未覆盖环境变量时回退到开发 JWT 默认值和 root 口令，日志出现 JWT 密钥过短警告。
5. **测试操作偏差**：第一次恢复演练把变量误写成 `DATABASE_URL`（项目实际为 `BACKEND_DATABASE_URL`），进程连到本机共享库并注册了一个合成账号；已停止并披露，未查询/修改真实用户数据。

本工作区已修：密钥必填与启动强校验、Nginx 限流配置。未闭环：后端端口仍发布、无版本化回滚脚本，需在目标环境验收。

### Phase 4 并发正式验收

- 新增混合旅程压测：登录后浏览课程/问题、搜索、详情、投票、通知，读写比固定。
- 阶段：5/10/25/50/75/100 VU 各 ≥10 分钟；100 VU 稳态 ≥30 分钟；突发 3 次；耐久 ≥2 小时。
- 门槛：P95 ≤800ms、P99 ≤2s、错误率 <1%、无 `QueuePool` 错误、资源无单调增长。

验收：报告含每阶段 RPS、P95/P99、错误分类、连接数、CPU/内存；未达标不勾完成。

### Phase 5 文档与状态

- 更新 `specs/requirements/R-004-*.md`、`tasks.md`、`status.md`、ADR（如有口径变更）。
- 审查记录写清“验证了什么、没验证什么、遗留什么”。

## 4. 已确认口径

1. **投票语义**：按 spec E-04 的 toggle。重复同值=取消，异值=改票；反馈中的 BUG-VOTE 重分类为测试口径误判。
2. **申诉入口**：页面放宽到“存在可申诉工单”，与后端一致。
3. **88 条失败**：重跑并重分类，补逐用例数据库断言后重新生成工作簿。
4. **部署范围**：本机不执行部署；只描述错误与目标环境清单，实际演练在目标服务器完成。
5. **并发门槛**：以 100 VU 混合旅程、稳态 ≥30 分钟、P95 ≤800ms、P99 ≤2s、错误率 <1% 作为发布门禁。

## 5. 建议顺序

Phase 0 → 确认未决项 → Phase 1/2 并行 → Phase 3 → Phase 4 → Phase 5。Phase 0 未完成前不改认证/投票代码，避免把正确实现改坏。
