# T-23E 高并发容量评估（1000 / 10000 并发）

日期：2026-11-28
范围：R-003 / ADR-013 / BUG-001 扩展压测

## 设计依据

- 用户要求：1000、10000 并发实测；worker 不写死 4C4G，启动时探测可用核。
- `docs/decisions/ADR-013-worker运行时探测.md`：`workers = max(1, min(CPU, 内存GB, DB_CONNECTION_BUDGET // 20))`，默认预算 100。
- `backend/app/core/workers.py`：计算逻辑与单测。

## 本轮改动

- 新增 `backend/app/core/workers.py` 与 `tests/test_workers.py`（4 项）。
- `docker-entrypoint.sh` 改为探测 CPU/内存并调用 `compute_workers`，输出实际 worker 数；`WORKER_MAX` 可再收紧。
- Compose 新增 `DB_CONNECTION_BUDGET=100`、`WORKER_MAX=0`。
- 压测脚本改为 asyncio + 原始 HTTP 连接，支持 1000/10000 并发（原线程池版本无法创建上万线程）。

## 验证记录

本机：16 CPU / 15GB，预算 100、每 worker 20 连接 → **5 worker、100 个数据库连接**；100 并发基线复测仍为 99.81% 成功率、P95 378.9ms。

### 1000 并发（60s，超时 30s）

```
total=3564 rps=41.1
success=509 success_rate=14.28%
latency_ms p50=23849.7 p95=30020.7 p99=30349.1 max=30454.0
statuses=network_error:408, 200:509, 503:2647
errors=TimeoutError:408
```

### 10000 并发（30s，超时 10s）

```
total=18877 rps=527.6
success=0 success_rate=0.00%
latency_ms p50=14903.6 p95=33042.7 p99=33269.9
statuses=network_error:18877
errors=ConnectionRefusedError:16119, TimeoutError:2758
```

## 结论与决策说明

- **1000 并发超出当前同步栈容量**：5 worker × 40 anyio 线程 = 200 个在途请求，其余在服务端排队；线程拿到槽位后等待数据库连接，超过 `pool_timeout=5s` 即 503（2647 次）。503 是保护性快速失败，避免请求挂到 30s 超时；408 次超时来自客户端等待过久。
- **10000 并发首先死在连接建立阶段**：Uvicorn 默认监听 backlog 2048，16119 次 `ConnectionRefusedError`；即使调大 backlog，同步线程池与 100 个数据库连接也无法承载。该结果不是数据库连接池问题，而是入口与执行模型的上限。
- **worker 改为运行时探测**：不再硬编码 4；4C4G 会得到 4 worker（预算允许时），16C15G 得到 5 worker（受数据库预算约束）。扩容 worker 前必须先提高 `DB_CONNECTION_BUDGET` 并同步 MySQL `max_connections`。
- **建议的后续方向**（不在本 Bug 范围）：入口排队/限流（Nginx `limit_conn` 或令牌桶）、读接口缓存、慢查询优化、异步数据库访问、水平扩容。1000/10000 并发不应作为 4C4G 单实例验收目标。
- **未验证**：调大 backlog/异步化后的上限、真实 4C4G 容器、多实例负载均衡。
