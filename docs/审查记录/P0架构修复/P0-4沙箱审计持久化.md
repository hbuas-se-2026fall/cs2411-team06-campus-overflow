# P0-4 沙箱审计后端持久化

日期：2026-11-20
范围：把 Agent 沙箱执行审计（P0-2 的结构化日志）接入 FastAPI `/internal/agent/*` 白名单接口持久化；不改沙箱决策与执行语义。

## 设计依据

- `docs/审查记录/P0架构修复/P0-2沙箱.md` 决策 5 与遗留：审计当前只写结构化日志，P0-4 接入后端持久化；事件字段已按“不泄密”设计。
- `AGENTS.md` 硬性约束 1：Agent 不直连业务 MySQL，只能调 FastAPI `/internal/agent/*`；硬性约束 5：run / tool call / approval request 必须可追踪，至少保留 trace id 与摘要。
- `specs/spec.md` SA-R03 / `specs/plan.md` AX-R09：子 Agent 外部执行在沙箱边界内，外部命令、浏览器、MCP、文件执行统一走沙箱且可追溯。
- `.trae/rules/coding-style.md`：接口字段蛇形、边界用 Zod / Pydantic 校验、不记录密钥与隐私原文、用户可见文案中文。
- `.trae/rules/conventions.md`：统一响应 `{ code, data, message }`；内部接口服务 token 鉴权并透传 `x-trace-id`。
- 现有实现：`agent/src/sandbox/executor.ts` 的 `SandboxAuditSink` 与 `SandboxAuditEvent`；`backend/app/modules/governance/{router_internal,service_internal,repository,models}.py` 的 T-12 白名单模式；P0-3 的迁移与反例测试写法。

## 实现

### 后端

- `governance/models.py`：新增 `agent_sandbox_events`——`event / outcome / tool / executable / command_digest / arg_count / action_class / network_mode / trace_id / duration_ms / output_bytes / reason_code / created_at`；系统级审计，**无 user_id 归属**。
- `governance/schemas.py`：
  - `SandboxEventCreateRequest` 严格 `extra=forbid`；枚举与长度受控（`tool ≤ 50`、`executable ≤ 128`、`trace_id ≤ 64`、`arg_count ≤ 1000`、`duration_ms ≤ 600000`、`output_bytes ≤ 10 MiB`）。
  - `command_digest` 只接受 16 位小写十六进制；`executable` 出现 `/` 或 `\` 直接拒绝（调用方不得带绝对路径）。
  - 结果与原因码联动：`completed` 不得带 `reason_code`，`denied/failed` 必须带固定原因码（与 Agent 契约同一枚举）。
- `governance/service_internal.py`：`record_sandbox_event` 追加写入并 commit；`trace_id` 缺省回落到请求头（`ServiceAuth` 已回写 `X-Trace-Id`），保证记录可检索。
- `governance/repository.py`：`insert_sandbox_event` 只增不改，出参 `SandboxEventOut(id)`。
- `governance/router_internal.py`：`POST /internal/agent/sandbox/events`，仅 `ServiceAuth`，不接受用户身份；返回“沙箱审计已记录”。
- `alembic/versions/p0d_sandbox_events.py`：接 `p0c_chat_streams`，建表 + `outcome / trace_id / created_at` 索引，可回滚。

### Agent

- `internal-client.ts`：新增 `SandboxAuditRecorder.recordSandboxEvent`（挂在 `createInternalClient` 返回值上，不扩大 `InternalClient` 接口，避免影响既有测试替身）；回执只校验 `id`。
- `sandbox/audit.ts`：`createBackendSandboxAudit` 把审计事件经服务凭证上报，单次 5 秒截止；失败只写 `sandbox_audit_delivery_failed` 结构化日志（outcome / tool / reason_code / trace_id），不含参数与响应正文。
- `sandbox/executor.ts`：`SandboxAuditSink` 允许返回 Promise；新增 `emitAudit` 旁路投放——同步抛错与异步失败都不影响拒绝/执行结果，也不产生未处理拒绝。
- `web/browser-reader.ts`：唯一外部进程入口注入后端审计 sink，浏览器读取与关闭各产生一条 `sandbox_exec` 审计。

## 决策说明

1. **系统级事件，不写 user_id**：沙箱审计描述的是进程执行边界，不是用户数据访问；写入用户归属反而会让审计看起来像授权依据。检索仍可用 `trace_id` 关联到 `agent_runs`。
2. **旁路 best-effort，不阻塞执行**：审计失败不能让沙箱拒绝变成 200，也不能让已完成的读取变成失败。执行器不 `await` 上报，sink 内部兜底日志；代价是进程在事件发出前崩溃会丢一条记录，已写入“遗留”。
3. **不做自动 TTL 清理**：审计是证据，不能像聊天流那样到期静默删除；保留周期交给运维/归档策略，本批只建索引。
4. **严格契约而非宽松接收**：宁可 400 也不接受带路径的执行名、未知原因码或 completed+reason 的矛盾组合，避免把不可解释的数据写进证据表。
5. **不扩大 `InternalClient` 接口**：新增 `SandboxAuditRecorder` 追加在工厂返回类型上，既有 `InternalClient` 测试替身无需补方法。
6. **不引入批量/队列**：当前唯一外部进程是浏览器读取，单事件直发足够；引入队列会在未验证真实流量前增加失败面。

## 遗留与限制

- 只做了写入；尚无管理端按 `trace_id / outcome / 时间窗` 查询的只读接口与页面（归 T-16 观测面板）。
- 上报为 best-effort：后端不可用或进程在发送前退出会丢失该条事件；只保留 `sandbox_audit_delivery_failed` 日志。
- 审计与 `agent_runs` 仅通过 `trace_id` 弱关联，未加外键；运行记录缺失时审计仍可独立成立。
- `sandbox-runner` 容器运行时尚未接入真实工具，容器侧执行暂不产生本表流量。
- 未做保留期/归档任务；表增长监控与清理策略需在部署阶段确定。
