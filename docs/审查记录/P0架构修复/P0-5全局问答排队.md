# P0-5 全局问答排队

日期：2026-11-20
范围：后端 `agent_slot_waiters` 排队票据与内部排队接口、Agent 排队客户端与全局问答准入、聊天排队提示、P0-1 槽位回收条件收紧。

## 设计依据

- 用户确认：全局问答配额超限时**排队等待**，不立即返回繁忙；跨实例共享问答槽。
- 架构评审 P0-1 遗留：chat 仍为每实例容量，未做跨实例全局问答配额。
- `.trae/rules/conventions.md`：内部接口只在 `/internal/agent/*`，服务 token 鉴权；Agent 不直连 MySQL。
- `specs/plan.md` AX-R09：8 槽为单实例上限；全局容量需独立机制，不引入 Redis。

## 实现

### 后端

- 新表 `agent_slot_waiters`（迁移 `p0e_slot_waiters`，`down_revision = p0d_sandbox_events`）：自增 `id` 作为 FIFO 序，记录 `kind/job_id/instance_id/capacity/ttl_seconds`、授予结果（`slot_no/fencing_token/granted_at`）与等待截止 `expires_at`。
- 新接口（仅服务 token）：
  - `POST /internal/agent/slot-leases/wait`：入队并尝试晋升；队首且有空槽直接返回租约，否则返回 `waiting` 与位置。
  - `POST /internal/agent/slot-leases/wait/{ticket_id}/poll`：已授予则取走租约并删除票据；等待中返回位置；到期返回 `expired`；票据不存在返回 404。
  - `POST /internal/agent/slot-leases/wait/{ticket_id}/cancel`：放弃排队；已授予但未取走的票据同时回收槽位。
- 晋升严格 FIFO：只处理同 kind 最早入队且未过期的队首，`FOR UPDATE` 锁队首后复用既有原子抢槽逻辑；过期队首机会式删除。授予后未被取走且租约已过期时回收槽位并作废票据。
- **收紧 P0-1 槽位回收条件**：原规则“同实例即可抢占未过期槽位”会让同一实例的多个请求互相顶替租约，从而绕过全局容量。现改为“已过期，或同一 `job_id` 的重试”，直接 claim 与排队晋升共用该规则。

### Agent

- `backend-lease.ts`：新增 `createSlotQueueClient`（enqueue/poll/cancel；poll 404 视为过期，cancel 404 幂等）与 `createQaAdmission`。
- `createQaAdmission`：先入队；`waiting` 时按 `pollMs`（默认 500ms）轮询，`onWaiting` 仅在位置变化时通知；超过 `maxWaitMs` 或运行信号取消时先放弃票据再抛 `QaQueueError`（中文文案）。轮询偶发失败不放弃票据，由截止时间兜底。
- `AgentPool`：新增 `qaAdmission` 与 `setQaAdmission`；`run(kind, jobId, run, options)` 支持 `signal`/`onWaiting`。问答任务先取全局租约，再进入本地 5 槽调度，结束时释放。
- `app.ts`：`AGENT_GLOBAL_QA_LIMIT > 0`（默认 0 不启用）时装配；`AGENT_QA_QUEUE_WAIT_MS`（默认 120000）控制排队上限。
- `routes/chat.ts`：排队时追加 `notice`（“问答并发已满，正在排队，前面还有 N 位”）；排队超时/取消分别透出中文 SSE error。

## 决策说明

1. **排队而不是繁忙**：用户明确要求超限时排队；本地 `PoolBusyError` 仍保留，用于本地等待队列超过 64 的极端情况。
2. **全局租约先于本地槽位**：与本项目 P0-1 治理准入保持一致；全局租约在本地排队期间也持有，容量配置应不低于“实例数 × 5”。
3. **严格 FIFO 而非抢占**：只由队首晋升，避免后到任务插队导致长等待；代价是队首放弃前会占住一次晋升机会，因此超时/取消必须主动 cancel。
4. **收紧 P0-1 回收条件**：同实例不同 job 不得互相顶替，否则全局容量形同虚设；同 job 重试仍可复用原槽位（后续 P0-6 追加 `retry_count` 预算，初始 5，每次顶替/重试 -1）。
5. **默认关闭**：`AGENT_GLOBAL_QA_LIMIT=0` 时行为与改造前完全一致，便于分批灰度。

## 遗留

- 排队等待计入 180 秒运行预算（`control.start()` 在入池前已开始），排队较久会压缩实际生成时间；默认排队上限 120 秒即为此预留。
- 全局问答租约 TTL 900 秒，未接自动续租；当前 180 秒运行预算内安全，若后续放宽运行时长需补心跳续租。
- 未做真实多实例排队验收；本轮为 SQLite 单测 + 本地迁移验证。
- 管理端池快照未展示“全局排队人数”，后续可经后端票据统计补充。
