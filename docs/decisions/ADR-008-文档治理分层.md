# ADR-008：规则、需求、状态、决策分层治理

- 状态：accepted
- 日期：2026-11-21
- 决策人：用户
- 取代：在规则文档内追加历史状态的做法
- 被取代：无

## 背景

规则、需求、进度与决策长期混写：`conventions.md` 头部叠加版本范围注，`project-context.md` 追加多段“最新增量”，`tasks.md` 同时承担待办、看板与决策记录。结果是同一事实多处不一致，审计与交接成本高。

## 决策

- 规则只写当前有效、可执行的约定，不写版本历史。
- `specs/status.md` 是唯一进度源；README、Wiki、AGENTS 只链接，不复制进度。
- 决策写入 `docs/decisions/ADR-*.md`，被取代时改状态并链接新编号，不覆盖旧文。
- `tasks.md` 只放原子任务、验收与证据链接；父任务不代替子项验收。
- 需求开工前必须满足 DoR，完成必须满足 DoD；阶段门为探索 → 决策 → 计划 → 实现 → 验证 → 发布。
- `specs/` 与 `docs/decisions/` 纳入 Git；其余 `docs/` 草稿继续本地保存。

## 后果

- 历史增量已迁移到 ADR，规则文档变短；后续状态变化只改 `status.md`。
- 需要持续维护 ADR 索引与状态页，否则会重新退化。
- 规则文件仍位于被忽略的 `.trae/` 下，是否纳入 Git 另行决定。
